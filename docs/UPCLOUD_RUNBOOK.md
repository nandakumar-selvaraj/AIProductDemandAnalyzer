# UpCloud provisioning and deployment runbook

These are future operator steps, **not actions executed in Phase 8A**.

## Before provisioning

Review PHASE8A_INFRASTRUCTURE.md, TERRAFORM_STATE.md and GITHUB_PRODUCTION_ENVIRONMENT.md.
Check current UpCloud plans/zones/templates, 2 CPU/4 GB sizing, regional capacity and full
compute/disk/IPv4/off-host/state quote. `UPCLOUD_PLAN` and `UPCLOUD_ZONE` have no default.
The controlled plan workflow checks current catalogs, not a guaranteed reservation/price.
Use an API-token subaccount limited to the necessary server/storage/firewall operations;
never use account-owner credentials or enable expensive services automatically.

Review public SSH key fingerprints. Deployer and operator key material must differ.
Restrict SSH CIDRs to real operator/static CI egress. Configure production reviewers and
branch restrictions, separate state credentials and encrypted versioned state first.
No local production credentials are generated by these files.

## Provision, obtain IP, then stop

1. Push reviewed code only when explicitly instructed; require all validation workflows.
2. Manually dispatch `terraform-plan.yml` on master. Review actions, current configuration
   and sanitized SHA256; raw plan is encrypted in the private bucket.
3. Explicitly dispatch/approve `terraform-apply.yml` with that run ID, exact SHA and plan
   SHA256. It rejects changed inputs, stale state/plans, replacements/deletes and wrong SHA.
4. Read the public IP/SSH outputs. Stop and arrange the friend's A record using
   TEMPORARY_SUBDOMAIN.md. This workflow has no application deployment step.
5. Through the independent operator key/console verify `cloud-init status --wait`, Docker
   Compose v2, storage mounted at `/var/lib/portfolio`, root/password SSH denial, restricted
   SSH access, UpCloud firewall/UFW, and no listening public app/DB/Ollama ports. Preserve
   console access until SSH hardening is confirmed. Never rerun bootstrap over existing data.

Boot uses virtio:0 for Ubuntu and virtio:1 (`/dev/vdb`) for the separate encrypted data
disk. Only an unformatted new device with no existing signatures is formatted; existing signatures cause
refusal or an ext4 mount. Validate this device mapping in the first authorized boot.
Docker data-root uses that mount with systemd mount dependencies; no silent root-disk
fallback is allowed. Server/storage prevent_destroy guards block accidental replacement.
Bootstrap/script updates after provisioning need a reviewed operator maintenance procedure;
do not recreate the server to update user-data or fix a hostname.

## Prepare private host configuration

As the operator, install root-owned mode-0600 `/etc/portfolio/demand.env` based on the
repository's `.env.production.example`. Generate independent strong passwords/signing
secret on the VPS through your approved secret manager; no values belong in Terraform,
cloud-init, GitHub artifacts or shell arguments. Preserve stable project name `demand`.
Use the private DB `demand` and owner/runtime roles, never the local admin database.
Keep PUBLIC_DEMO_ENABLED, DEMO_AI_ENABLED and AI_ENABLED false. The entrypoint derives
hostname/origin/image fields from the reviewed release rather than trusting stale env values.

Install `/etc/portfolio/backup.env` and a separate root-only Restic password file; see
deploy/ops/backup.env.example and BACKUP_RESTORE.md. Approve/create a dedicated encrypted
off-host repository and explicitly initialize Restic with its separate credentials. No
backup cloud account/bucket is created automatically. Verify access before deployment.

Make reviewed GHCR images publicly pullable or install narrowly scoped read-only pull
credentials on the host. Pin POSTGRES_RUNTIME_IMAGE after the initial verified build.
Database image changes are deliberately blocked by normal deployment; patch/major upgrades
need a separate backed-up, restored and reviewed maintenance procedure, not an app rollback.

## Deploy tested digests, not source or latest tags

The image workflow runs only after Backend CI, synthetic E2E, disposable Docker validation
and Terraform validation pass for the same master SHA. It publishes immutable backend/
frontend digests, scans them and the pinned PostgreSQL/Caddy candidates, then records a
non-secret release manifest. A failed scan or missing manifest is not a releasable build.

After valid DNS and host setup, manually dispatch/approve `production-deploy.yml` using
the successful image-build run ID and full commit SHA. Use a trusted reachable runner.
It validates Environment protections, CI/provenance, DNS and pinned SSH identity. The
restricted entrypoint pulls approved digests, starts private PostgreSQL, streams an
encrypted off-host backup, restores it into a new verification database, runs migrations,
starts healthy app services and shared Caddy, then checks HTTPS/ready/anonymous denial.
There is no `up --build`, source checkout on the VPS, schema downgrade or volume deletion.

After migration, an operator must provision the Admin with the existing CLI, using an
interactive password prompt or approved stdin secret source, never command arguments:

```sh
# Run from a root-only shell with the reviewed release's environment loaded by an approved
# secret manager. Use the installed base/overlay, stable project name and existing images.
docker compose --project-name demand -f /usr/local/lib/portfolio/compose.production.yml \
  -f /usr/local/lib/portfolio/compose.app.yml run --rm migrate \
  python -m scripts.manage_users create --email "$ADMIN_EMAIL" --role admin
```

No default credentials or users are created, and the local Admin is not transferred.
Provision a Viewer independently if needed. Test cookie flags, CSRF, upload denial and
expiry; restricted CLI API tokens remain revocable and public Swagger remains blocked.

## Failure and rollback

Inspect Actions summary and root-only host status. The script intentionally suppresses
raw subprocess output because it may contain credentials; do not upload environment,
database dumps, SSH keys or unredacted container logs to Actions artifacts.

For app rollback, manually dispatch/approve operation `rollback` using the older successful
build run and SHA. The host must have a matching previously successful local release.
Only backend/frontend/commit roll back; current DB image, schema, ingress and active domain
remain. Verify that the older app is schema-compatible first. If not, forward-fix or
restore into a NEW database/stack and verify before an explicit connection cutover.
No automatic downgrade, database overwrite, `down -v`, image prune or Terraform destroy.

Changes to the active domain use the separate hostname lifecycle guide. Back up signing
and backup keys separately; restoring old session state may require deliberate JWT key
rotation. Preserve the original database and snapshot for recovery until verified.

## Operations

Review `systemctl list-timers`, `journalctl -u portfolio-backup -u portfolio-monitor`,
`systemctl --failed`, `docker stats`, `df -h` and `ss -lntup`. Monitor thresholds: <15%
free data disk, <10% available RAM, sustained load >2x CPU count, TLS <7 days, backup age
>26h. Security updates install automatically; kernel/Docker reboot is operator-scheduled.
Keep Docker/Compose on supported patched versions and review cloud firewall rules after
changes. UpCloud's firewall is authoritative for public Docker traffic; UFW alone does
not cover Docker NAT publication. Only 80/443 may be published; verify externally from
an approved host, and SSH only from allowed CIDRs. Configure approved off-host alerting
before launch; local journald output alone cannot detect total VPS/network failure.
